NGO Works Portal — Master Plan (A to Z)

Goal: one secure internal platform where HQ, project staff, finance, M&E, field officers, donors and implementing partners run projects, grants, approvals and reporting, with no scattered spreadsheets.

Honest framing: "multi-million dollar standard" comes from the process (security, testing, review, backups, documentation), not just the tech stack. This plan builds all of that in. You will use Antigravity (AI agent IDE) to write most code, so the plan is designed around a mainstream stack the AI knows extremely well, and around guardrails that catch AI mistakes.

1. Guiding principles

  1. Boring, popular technology. Widely used tools = better AI output, easier hiring later.
  2. Managed services over self-hosting. No servers for you to patch.
  3. Security by default. Beneficiary data is sensitive; donors will audit you.
  4. Field-first. Phone-friendly, low-bandwidth, works offline.
  5. Vertical slices. Build one complete feature at a time (database → screen → tests), never everything half-done.
  6. Build vs integrate. Do not rebuild what exists: for heavy survey/offline data collection, integrate KoboToolbox or ODK later; build the core workflow system yourself.

3. Modules and priorities

MVP (Phases 1–3): must-have

  1. Login & access control — email login, MFA, roles, per-project permissions
  2. Master data — donors, grants, projects, partners, staff, locations (Division → District → Upazila → Union → Village)
  3. Project lifecycle board (Kanban) — Concept → Proposal → Approved → Implementation → M&E → Closure, with stage-gate checklists
  4. Logframe / results framework — Goal → Outcome → Output → Activity → Indicator (target, baseline, actual, dates)
  5. Work plan & tasks — activities with owners, deadlines, status, comments
  6. Field reporting (mobile PWA, offline) — daily/weekly forms, photos, GPS, sync later
  7. Budget & grant tracking — budget lines, spent vs remaining (burn rate), donor deadlines
  8. Approval workflows — Field Officer → Project Manager → Finance Director, with stamp/time/comment at each step
  9. Expense & receipt upload — drag-and-drop, phone camera, OCR to auto-read date/amount (staff confirms)
  10. Document library — versioned files, templates, donor report formats
  11. Notifications — in-app + email (deadline reminders, pending approvals)
  12. Audit log — who changed what, when (append-only)

Phase 4–5: strong additions 13. Donor portal — per-donor dashboard, approved reports, financial summaries 14. Beneficiary registry — with duplicate detection, consent record, restricted access 15. Where to host the app (pick one, decide in Phase 0):

  • Option A (recommended for simplicity): Vercel for Next.js, with Cloudflare in front for DNS/WAF. Smoothest deploys for Next.js.
  • Option B (Cloudflare-native): Cloudflare Workers using the OpenNext adapter. Cheaper and one vendor, but Next.js on Workers has more edge cases; needs a bit more care.
  • Option C (max control): a VPS (Hetzner/DigitalOcean) with Docker. Only if you get a DevOps person; more work for you.

Approximate running cost at your scale (verify current prices before buying): domain ~$15/yr; Supabase Pro ~$25/mo; Vercel Pro ~$20/user/mo or Cloudflare Workers paid ~$5/mo; Cloudflare Pro optional ~$25/mo; GitHub Team ~$4/user/mo; Sentry free–$26/mo; email ~$0–20/mo. Realistic total: $60–200/month at start, far below the cost of the people who build it.

Cloudflare Access / Zero Trust (free tier for small teams) can additionally lock the admin area behind a second gate.

6. Security and compliance (the "multi-million" part)

  • Row-Level Security (RLS) in PostgreSQL: even a code bug cannot let a field officer read another region's data.
  • MFA required for Finance, Admin, Management; recommended for all.
  • Least privilege: roles above; donor and partner accounts strictly scoped.
  • Encryption: HTTPS everywhere, data encrypted at rest; sensitive beneficiary fields (national ID, phone) additionally encrypted at column level.
  • Audit log: append-only table; every create/update/delete/approval recorded with user, time, before/after.
  • Backups: daily automatic + point-in-time recovery; restore drill every quarter (a backup you never tested is a hope, not a backup).
  • Secrets never in code; stored in vendor secret managers.
  • Rate limiting + Turnstile on login; WAF rules in Cloudflare.
  • Data protection: consent capture for beneficiaries, retention rules, deletion process. Check applicable Bangladesh law and your donor agreements' data clauses (donors in Turkey/Canada may impose their own rules).
  • Before go-live: independent penetration test + code security review by a human professional. Budget for this; it is non-negotiable for a portal holding beneficiary and financial data.
  • Incident plan: one page: who is called, how to revoke access, how to restore.

7. Core database design (main tables)

organizations (donors, partners) · users · roles · user_project_access · grants (donor, amount, currency, dates) · projects · project_stages · budget_lines · expenses · approvals (workflow steps) · receipts · logframe_nodes (goal/outcome/output/activity) · indicators · indicator_values · activities / tasks · field_reports · report_attachments · beneficiaries · beneficiary_participation · locations (BD admin hierarchy) · documents (+ versions) · notifications · audit_log · exchange_rates.

Design rules: every table has id, created_at, created_by, updated_at; use soft-delete (mark deleted, never erase); money stored as integers/decimals with currency code.

8. Key workflows

Expense approval: Field Officer submits (photo receipt) → OCR pre-fills → Project Manager reviews → Finance verifies against budget line → Finance Director approves → status "Approved" → payment recorded. Every step: stamp, time, comment; rejection returns to sender with reason. Auto-escalate if pending more than N days.

Field report: Officer fills form offline → saved on phone → auto-syncs when online → Project Officer reviews → M&E validates indicators → feeds dashboards and donor reports.

Donor reporting: indicators + financials roll up automatically → report generator fills the donor's template → Programme Manager approves → published to donor portal.

10. How to work with Antigravity as a non-expert

  1. Write the spec first. Keep a /docs folder: requirements, roles, database design, workflows. Give it to the agent as context.
  2. Create a rules file (e.g., AGENTS.md) telling the agent: use TypeScript, Next.js, Tailwind, shadcn/ui, Drizzle; every table needs RLS; never hardcode secrets; write tests for each feature; small changes only; explain what changed.
  3. One feature per branch. Ask the agent to implement one slice, run tests, open a pull request on GitHub. Never commit straight to main.
  4. Turn on protections: branch protection on main, required passing tests, Dependabot (dependency alerts), secret scanning.
  5. Use a second AI as reviewer: ask a different model/session to review each pull request for security and bugs. It catches many mistakes.
  6. Test with real people early on staging, using fake data.
  7. Ask the agent to explain anything you do not understand; keep a DECISIONS.md log of why choices were made.
  8. Hire a senior reviewer part-time (even 5–10 hrs/month) for architecture and security reviews. This is the best money you can spend.

Starter prompts (Phase 1):

  • "Read /docs and propose the folder structure and a task list for Phase 1. Do not write code yet."
  • "Set up Next.js + TypeScript + Tailwind + shadcn/ui, ESLint, and a GitHub Actions workflow that runs lint and tests."
  • "Design the Postgres schema for users, roles, projects, grants, with RLS policies so users see only assigned projects. Include tests proving a user cannot read another project's rows."

11. Quality, DevOps, operations

  • Testing: unit tests (logic), integration tests (database and RLS), end-to-end tests with Playwright for critical flows (login, submit expense, approve).
  • CI/CD: GitHub Actions runs tests on every pull request; merge to main deploys to staging; a manual click promotes to production.
  • Monitoring: Sentry, uptime checks, database usage alerts.
  • Performance for Bangladesh: small page sizes, image compression on upload, caching via Cloudflare, offline-first field forms, test on a mid-range Android phone with a slow connection.
  • Documentation: user guide (English + Bangla), short training videos, admin runbook, developer README.
  • Training: role-based sessions; appoint one "portal champion" per office.
  • Data migration: clean existing spreadsheets, import through scripts in staging first, reconcile totals before go-live.
  • Change management: run old and new systems in parallel for one reporting cycle.

13. Your first 14 days

  1. Create a GitHub organization and private repo; enable branch protection.
  2. Buy the domain; put it on Cloudflare.
  3. Create Supabase project (Singapore or Mumbai) for staging.
  4. Interview 5–8 users (field officer, finance, PM, M&E, one donor contact); collect their current forms and reports.
  5. Write the requirements and role matrix in /docs.
  6. Sketch wireframes for 5 screens: dashboard, project Kanban, field report, expense approval, donor view.
  7. Set up Antigravity with the rules file; run the first "propose the plan" prompt.
  8. Decide hosting (Option A/B/C).

14. Decisions to make in Phase 0

  • How many total users, and how many field officers?
  • Approximately how many beneficiaries and projects per year?
  • Which donors need custom report formats, and in which languages and currencies?
  • Which regions have poor or no connectivity?
  • Who is the business owner who approves scope (not just you)?
  • Is there budget for a pen test and a part-time senior reviewer?
  • Any donor rules on where data must be stored?
